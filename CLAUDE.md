# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
bundle install                        # install nokogiri (only needed for the scrape step)
bundle exec ruby scrape_sanskrit.rb   # step 1: fetch site + download mp3s -> data/
ruby fetch_gita.rb                    # step 1b: fetch Bhagavad Gita verses + recitation mp3s -> data/
./main.rb --all                       # step 2: generate every category's import file
./main.rb --basic --combinations      # generate a subset (flags combine)
./main.rb --list                      # list categories
./main.rb --help
```

**The generated `sanskrit_*_anki.txt` deck files are committed to the repo.** They are build artifacts of `data/*.json`, so whenever you change a data file (or a generator), you MUST regenerate the affected deck(s) and commit the updated `.txt` alongside the data change — a data edit without its regenerated deck is an incomplete commit. Run the matching generator (e.g. `./main.rb --vowel-sandhi` after editing `data/vowel_sandhi.json`, or `./main.rb --all` to be safe) and include the resulting `sanskrit_*_anki.txt` diff in the same commit.

Unit tests for the pure transforms and shared primitives live in `test/` (minitest, a Ruby default gem); run a file with `ruby test/<name>_test.rb`. There is no linter or build step. `main.rb` uses only the Ruby standard library; only `scrape_sanskrit.rb` needs `nokogiri` (`fetch_gita.rb` uses `open-uri`, also stdlib). Categories that emit `[sound:...]` tags (`--basic`, `--gita-verses` and `--mantras`) prompt interactively before copying audio. The alphabet categories depend on `data/letters.json` (from `scrape_sanskrit.rb`); `--gita-verses` depends instead on `data/gita.json` (from `fetch_gita.rb`, but committed) and declares `requires_letters? == false`, so a Gita-only run needs no alphabet scrape. `--gita-verses` also needs no `fetch_gita.rb` run at all: `data/gita.json` is committed and the (uncommitted) recitation mp3s are pulled transparently from a GitHub release the first time you copy them (see "Bhagavad Gita recitation audio is downloaded transparently" below). `fetch_gita.rb` is now only for *rebuilding* that data from the original sources.

## Architecture

Pipeline producing Anki import files for learning Sanskrit: the alphabet, numbers, a Vedānta glossary, the three sandhi families (joining and splitting), the case functions, the declensions, mantras and the Bhagavad Gītā. Every category generator is a pure transform over a committed file in `data/` — `data/letters.json` for the alphabet categories, and its own JSON source of truth for every other deck. Only the standalone fetch scripts touch the network: `scrape_sanskrit.rb` (alphabet) and `fetch_gita.rb` (Gītā); the generated `sanskrit_*_anki.txt` files are committed too.

1. **`scrape_sanskrit.rb`** scrapes <https://enjoylearningsanskrit.com/sanskrit-alphabet-tutor/> and downloads mp3s from `sanskritserver.kautukam.com`, writing `data/letters.json` + `data/audio/*.mp3`. It stays a standalone script — not a `main.rb` subcommand — since it is the only networked step.
2. **`main.rb`** is the single entry point for generation. It parses `--<category>` flags (or `--all`), loads `data/letters.json` once if any selected generator needs it (`requires_letters?`), runs each selected generator, then runs the audio-copy step if any generator referenced audio. Generators live in `lib/generators/` and share helpers in `lib/`.

### Module layout

- **`lib/paths.rb`** — filesystem locations (project root, `data/`, `data/audio/`, `letters.json`) plus `Paths.output`/`Paths.data` resolvers. `lib/` sits directly under the project root, so the root is `..` from these files.
- **`lib/letters.rb`** — `Letters.load` (reads `data/letters.json`, `abort`s with the "run scrape first" message if missing) and `Letters.by_id` (the same letters keyed by internal id). The single reader of the source data.
- **`lib/anki.rb`** — shared card primitives and every deck name constant, including the alphabet parent `Anki::DECK` (`🕉️ Sanskrit Alphabet`). `Anki.glyph_front(text)` builds the centered five-deep nested-`<big>` glyph; `Anki.write_deck(path, rows)` writes the identical 6-line header + tab-separated rows (flattening stray tabs in fields to spaces); `Anki.write_json` writes the pretty-printed JSON intermediate. A row may carry a 4th element naming its own deck — then every row must, and the file gets a `Deck` column (`#deck column:4`) instead of a `#deck:` header; `write_deck` raises if only some rows have one.
- **`lib/media.rb`** — the Anki media-folder discovery and audio-copy flow (see "Anki media folder discovery" below). `Media.copy_audio(filenames)` is a no-op when the list is empty.
- **`lib/generators/base.rb`** — `Generators::Base`, the common run loop. A subclass declares constants (`KEY`, `DESCRIPTION`, `OUTPUT_TXT`, optional `OUTPUT_JSON`) and implements `build` (the entry array, also written to the JSON intermediate when `OUTPUT_JSON` is set), `card(entry)` (returns `[key, front, back]`), and optionally `audio_files(data)`. `run` writes the files and returns a summary hash for `main.rb`'s consolidated report.
- **`lib/generators/{basic,combinations,conjuncts,anusvara}.rb`** — the four alphabet categories, one class each, holding their own domain constants. They fill the numbered subdecks of `🕉️ Sanskrit Alphabet` (see "Deck layout"): `basic` gives `1. Vowels` and `2. Consonants`, naming each row's deck — a letter whose first property is `Vowel` is a vowel (including aṁ/aḥ), everything else (including kṣa/jña) a consonant; then `3. Combinations`, `4. Conjuncts`, `5. Anusvāra` (constants `Anki::ALPHABET_*_DECK`).
- **`lib/generators/*.rb` (the rest)** — one generator per deck or subdeck, each a pure reader over its own committed `data/*.json` through a small loader module in `lib/` (`Vedanta`, `VowelSandhiDeck`, `CaseFunctions`, …). Each is documented in its own section below.

Adding a category means writing one `lib/generators/<name>.rb` subclass and registering its class in the `GENERATORS` array in `main.rb`; the `--<KEY>` flag, `--all`, `--list`, and (if it emits `[sound:...]`) the audio prompt all follow automatically.

### Deck layout

Every deck family is a single entry in Anki's deck list: a family with several parts is a **parent deck with numbered subdecks**, nested with Anki's `::` in the `#deck:` header. The numbers exist because Anki sorts subdecks alphabetically; they make that order the learning order. All names live as constants in `lib/anki.rb`, and `test/anki_test.rb` pins the nested layouts.

```
🕉️ Sanskrit Alphabet         ::1. Vowels  ::2. Consonants  ::3. Combinations  ::4. Conjuncts  ::5. Anusvāra
🕉️ Sanskrit Numbers
🕉️ Vedanta Glossary
🕉️ Sanskrit Sandhi Joining    ::1. Vowel  ::2. Visarga  ::3. External Consonant  ::4. Internal Consonant
🕉️ Sanskrit Sandhi Splitting  ::1. Vowel  ::2. Visarga  ::3. External Consonant  ::4. Internal Consonant
🕉️ Sanskrit Case Functions    ::1. Names  ::2. Uses  ::3. Examples
🕉️ Sanskrit Declensions       ::1. Endings  ::2. Shared Endings  ::3. त्-Ending Nouns
🕉️ Sanskrit Mantras
🕉️ Bhagavad Gita
```

Each generator writes one file and normally names one deck (`Generators::Base#deck`). The exception is `--basic`, whose one file holds both `1. Vowels` and `2. Consonants`: its rows carry a 4th element naming their own deck, which `Anki.write_deck` turns into a `Deck` column (`#deck column:4`).

**Renaming a deck constant does not move cards a user has already imported.** Anki applies the deck from an import file only to *new* notes; existing notes (matched by the `#guid column:1` key) are updated in place but stay in whatever deck they are in. So after any rename, tell the user to rename the existing deck inside Anki to the new name (renaming keeps review history), and regenerate + commit every affected `sanskrit_*_anki.txt`. Re-importing also never *deletes* a card a later version stopped generating, so a long-lived collection can hold orphans of dropped cards.

### Audio copy is data-driven

`main.rb` does not hardcode which category has audio. Each generator's `run` reports the audio filenames its cards referenced via `audio_files` (the basic alphabet returns every letter's `audio_file`, the Gītā and mantra decks their clips; the rest return `[]`). `main.rb` unions these across the run and, if non-empty, invokes `Media.copy_audio`. So if a future category gains `[sound:...]` cards, the copy prompt appears with no change to `main.rb`.

### Anusvāra cards are keyed to the following consonant

Anusvāra (ं) is realised as the nasal homorganic with the **following** sound, not the syllable it is written on, so `lib/generators/anusvara.rb` makes one card per following consonant rather than per syllable. The driving constant `ANUSVARA_RULES` groups the 33 consonants by articulation class: before a stop the mark becomes that varga's nasal (guttural→ṅ, palatal→ñ, retroflex→ṇ, dental→n, labial→m, via `:nasal_id`); before a semivowel/sibilant/`ह` there is no stop nasal so it stays a nasalised vowel (`:nasalized`). Each group carries a worked example (e.g. शंकर śaṃkara → śaṅkara). Rules were checked against Wikipedia "Anusvara" and ashtangayoga.info. The script also emits a few standalone vowel+mark recognition cards from `INDEPENDENT_MARKS` — only the three forms (ओं, आः, इं) the corpus count found attested; the rest of the independent vowel×{anusvāra,visarga} grid never occurs, so it was dropped from the combinations deck. Visarga (ः) sandhi is conditioned by the preceding vowel too, so it is not handled here; it has its own deck (see "The visarga sandhi deck").

### Conjuncts are computed via the virama

`lib/generators/conjuncts.rb` builds each ligature the same deterministic way as the combinations: a conjunct's Devanagari is its component consonants joined by the virama `्` (U+094D), and its IAST is each component's `roman` with the trailing inherent `a` dropped from every component *except the last* (`pa` + `ra` → `p` + `ra` = `pra`). The driving constant is `CONJUNCTS` — an ordered list of `[component_ids, frequency]` pairs where each ID is a `letters.json` consonant key. Frequencies are Ulrich Stiehl's Mahābhārata corpus rates (per-half-verse occurrence, so they don't sum to 100%); the list is the >1% subset, sorted high→low. `kSha`/`jJNa` are deliberately excluded because they already exist in `letters.json`. The component→ligature composition was validated row-for-row against the 360-conjunct table on Wikipedia's "Devanagari conjuncts" page (all 89 matched exactly), so if you add a conjunct, supply its `component_ids` and the virama join handles the glyph.

### The letter-ID spine

`scrape_sanskrit.rb` is built around `ALL_LETTERS` — an ordered list of internal IDs (`a`, `aa`, `RRi`, `kSha`, …). Four constants are keyed by that same ID: `DEVANAGARI`, `ROMAN` (IAST transliteration), `AUDIO_FILES` (remote filename), and runtime-derived `properties` / `tips`. Adding or renaming a letter means touching every map in lockstep.

`build_properties` derives grammatical metadata (Vowel/Consonant, Short/Long, Voiced/Aspirated, place of articulation) from the source page's CSS classes (`clm1`–`clm4`, `nasel`, `semi`, `sibi`, `clm8`, `short`/`long`/`guna`/`vriddhi`/`anusvara`/`visarga`) and the parent element's `id` (`place1`–`place5`, `vowels1`/`vowels2`/`amaha`). Any HTML structure change upstream will silently produce empty property lists — `extract_properties` reports counts so watch the "Found properties for N/M" line.

### Combinations are computed, not scraped

`lib/generators/combinations.rb` synthesizes consonant×vowel syllables purely from Unicode — no source page involved. A combined glyph is `consonant["devanagari"] + matra` (matras live in `VOWEL_MATRAS`, keyed by vowel ID), and its IAST is the consonant's `roman` with its trailing `a` replaced by the vowel's `roman`. The inherent `a` vowel is deliberately omitted because bare consonants already carry it and live in the basic deck. The `aM`/`aH` "vowels" are kept — they attach the anusvara/visarga sign to the inherent `a` (कं, कः); standalone vowel+mark forms instead live in `lib/generators/anusvara.rb`.

Watch the back-of-card breakdown logic in `components_devanagari`: the `aM`/`aH` marks are rendered on the dotted circle U+25CC (`◌ं`, `◌ः`) because the `letters.json` forms (अं/अः) carry a spurious leading `a` that would mislead.

Consonant×vowel combinations are pruned by corpus frequency: `COMBINATION_FREQUENCY` holds the Mahābhārata count of every consonant→vowel akṣara (same corpus/method as the conjuncts), and `build_combinations` drops any syllable below `MIN_FREQUENCY` (default 1, i.e. never attested). This cuts 112 of the 490 grid cells — almost entirely the vocalic vowels ḷ (`LLi`) and ṝ (`RRI`) and the nasals ṅ (`GNa`)/ñ (`JNa`), which never independently carry a vowel — leaving 378. Each surviving combo records its `mahabharata_count` in `combinations.json`. Raise `MIN_FREQUENCY` to prune rare syllables too. The vowel×{anusvara,visarga} set is **not** frequency-filtered.

### The Bhagavad Gita verse deck

A deck (`🕉️ Bhagavad Gita`, the constant `Anki::GITA_DECK`) separate from the alphabet. `fetch_gita.rb` is a standalone networked script (sibling of `scrape_sanskrit.rb`) that downloads the [`gita/gita`](https://github.com/gita/gita) open dataset — `verse.json` (Devanagari `text`, IAST `transliteration`, word-by-word `word_meanings`), `translation.json` (multi-author English/Hindi), `chapters.json`. `GitaDataset.build` (`lib/gita_dataset.rb`) is the pure join/filter that selects the two configured English translations (literal = Swami Gambirananda, devotional = Swami Sivananda — change the constants at the top of `fetch_gita.rb` to swap; the script aborts if a chosen author is missing for any verse). The dataset has 701 verses (one more than the canonical 700 — an edition artifact).

Verses are then merged into **bhagavadgita.com's canonical groups** by `GitaGroups.build` (`lib/gita_groups.rb`), driven by the hardcoded `GITA_VERSE_GROUPS` — 49 `[chapter, start, end]` ranges (e.g. `[1,4,6]`) that Swami Mukundananda's edition combines, covering exactly the 110 grouped verses with no gaps/overlaps. 701 verses → **640 cards** (591 singles + 49 groups). `data/gita.json` is therefore **group-level**: each record has `chapter`, `verse_label` (`"4-6"`/`"7"`), `verses[]`, merged `devanagari`/`transliteration`/`translations`, per-verse `word_meanings[]` (kept for a future word deck), and `audio_file`. `data/gita.json` is committed like the other `data/*.json`.

Audio is the **JKYog (Swami Mukundananda) recitation** (`https://gita-audio.jkyog.org/audio/sanskrit/gita_audios/`, 320 kbps — clearer than the gita/gita `verse_recitation` files). Each card maps to one clip by a deterministic URL — `JkyogAudio.naive_url(ch,v)` (`002_047.mp3`) for singles, `JkyogAudio.range_url(ch,s,e)` (`001_004-006.mp3`) for groups (`lib/jkyog_audio.rb`) — so `fetch_gita.rb` never scrapes. MP3s download to `data/gita_audio/gita_<cc>_<vv>.mp3`, zero-padded for sane filename sorting (e.g. `gita_01_07.mp3`, `gita_01_04-06.mp3`); the local name is set by `GitaGroups` (`format("gita_%02d_%02d.mp3", …)`), distinct from the remote JKYog name. `data/gita_audio/` is **gitignored** (640 files, ~289 MB — too large to commit); `fetch_gita.rb` skips files already present, so clear the folder to re-download after a source change.

### Bhagavad Gita recitation audio is downloaded transparently

Because the mp3s aren't committed, the whole `data/gita_audio/` folder is packaged as one **tar.gz attached to a GitHub release** (tag `gita-audio-v1`, asset `gita_audio.tar.gz`, on `mdayaram/anki-sanskrit`) and pulled on demand, so `./main.rb --gita-verses` works with no `fetch_gita.rb` step. `lib/gita_audio_archive.rb` (`GitaAudioArchive.ensure_present!`, stdlib-only) downloads the asset (`URL` constant) and extracts it into `data/`.

Wiring: `Generators::Base` has an `ensure_audio!` hook (default no-op, since the alphabet audio *is* committed) exposed in the run-result as `:ensure_audio`; `GitaVerses#ensure_audio!` delegates to `GitaAudioArchive`. `Media.copy_audio` takes an `ensure_present:` callable and invokes it **only after the user confirms the copy and only if some referenced files are missing** from the source dir — so the 289 MB download never happens unless it's actually needed. `main.rb` passes each `audio_dir` group's `:ensure_audio` callables through as `ensure_present`. The archive root is `gita_audio/`, so extraction is `tar -xzf <tmp> -C data/`. On any download/extract failure the module prints a "run `ruby fetch_gita.rb`" fallback and returns false instead of raising.

**Why tar.gz, not zip:** `main.rb` is standard-library-only and Ruby ships no zip reader; `tar` is the one archive tool present by default on macOS, Linux, and Windows 10+ (`unzip` is not). The module shells out to `tar`.

**To re-cut the archive** after changing the audio source: rebuild `data/gita_audio/` (`ruby fetch_gita.rb`), then from `data/` run `tar -czf gita_audio.tar.gz gita_audio`, create a new release (`gh release create gita-audio-v2 gita_audio.tar.gz …`), and bump the `URL` constant in `lib/gita_audio_archive.rb` to the new tag.

`lib/generators/gita_verses.rb` (`--gita-verses`) is a pure transform over the group-level `data/gita.json` (read via `Gita.load`, `lib/gita.rb`): key `gita_verse:<ch>.<verse_label>`, front is the merged Devanagari shloka(s), back is IAST + literal + devotional + `[sound:...]`. It overrides `deck`, `audio_dir` (→ `data/gita_audio`), and `requires_letters?` (→ false). It writes no JSON intermediate — `data/gita.json` already is one. Multi-deck/multi-audio-folder support that this added to shared code: `Anki.write_deck` takes a `deck:` kwarg, `Generators::Base` exposes `deck`/`audio_dir`/`self.requires_letters?`, `Media.copy_audio` takes a `source_dir:` kwarg, and `main.rb` loads `letters.json` only when a selected generator needs it and copies audio grouped by each generator's `audio_dir`. The generator builds card HTML by converting source newlines to `<br>` (multi-line verses/prose) — `write_deck` also flattens stray tabs/newlines defensively.

### The Vedanta glossary word deck

A deck (`🕉️ Vedanta Glossary`, `Anki::VEDANTA_DECK`) of ~2,393 single Sanskrit terms — front: Devanagari; back: IAST + English meaning; no audio. Unlike the alphabet and Gītā decks there is **no committed networked fetch**: `data/vedanta.json` is the **source of truth**, built once from the arshabodha "Vedanta-Sanskrit Glossary" PDF (Swami Dayananda) by the disposable scripts in `bootstrap/` and then QA-corrected. The PDF's Devanagari is an unrecoverable glyph font, so `bootstrap/extract_vedanta.py` (Python + pypdf) recovers only the IAST headword (via a WinAnsi→IAST decode map, separating columns by font) and English definition; the Devanagari column was generated once by IAST→Devanagari transliteration (the now-removed `to_devanagari`) and is now the hand-maintained Devanagari in `data/vedanta.json`, validated by `valid_pair?` in `test/vedanta_data_test.rb`. The `bootstrap/` scripts are not part of the runtime and may be removed.

`lib/iast_devanagari.rb` is a committed, tested **Devanagari→IAST reader** (`to_iast`) plus a pair validator (`valid_pair?`), reusable beyond this deck. There is deliberately **no IAST→Devanagari direction**: it is one-to-many (a homorganic nasal cluster can be written with the explicit conjunct अहङ्कारः or an anusvara अहंकारः, both valid for the same IAST `ahaṅkāraḥ`), so the Devanagari is **curated in the data files, not generated**. `to_iast` instead **canonicalises the reverse** direction (many-to-one) by realising anusvara-before-a-stop as the homorganic nasal (`ं` + क → `ṅk`; before a sibilant/semivowel/`ह` it stays `ṃ`), so both spellings above read to the same IAST. It also reads `ॐ` (U+0950) as `oṃ` — a single sign for a whole syllable, not a spellable sequence. `valid_pair?` compares `to_iast(dev)` against the IAST **modulo whitespace around the avagraha apostrophe**: the elided vowel is ऽ with no space in Devanagari (नरोऽपि) but the scholarly IAST convention puts a space before the apostrophe (`naro 'pi`, as Whitney writes it), so both IAST spellings validate; `to_iast` itself stays a faithful character reader (it never invents a space — `to_iast("नरोऽपि") == "naro'pi"`), and this leniency was added for the visarga-sandhi deck. A second, **opt-in** leniency exists for running text: `valid_pair?(iast, dev, ignore_spacing: true)` compares modulo *all* whitespace, because a mantra or verse is written sandhi-joined in Devanagari (तत्सवितुर्वरेण्यं) while its IAST separates the words for the reader (`tat savitur vareṇyaṃ`). The Devanagari is read **first** and the spaces dropped afterwards, so an anusvara is still resolved at the boundary as actually written (वरेण्यं before a space stays `ṃ` and does not become the homorganic `m` of a cluster). It is off by default: within a single word, differing spacing is a real mismatch. Added for the mantra deck. A curated `(iast, devanagari)` pair is trusted iff `valid_pair?(iast, dev)`, which accepts *every* valid spelling — this is why `data/vedanta.json` can store the anusvara Devanagari (अहंकारः) alongside the homorganic IAST (ahaṅkāraḥ), enforced by `test/vedanta_data_test.rb`. `lib/generators/vedanta.rb` (`--vedanta`) is a pure transform over `data/vedanta.json` (via `Vedanta.load`, `lib/vedanta.rb`): key `vedanta:<iast>`, no audio, `requires_letters? == false`.

`data/vedanta.json` was QA'd in three layers: structural + pair-validity (every `(iast, devanagari)` pair satisfies `IastDevanagari.valid_pair?`, enforced by the committed `test/vedanta_data_test.rb`; the disposable `bootstrap/qa_vedanta.rb` does the same `to_iast(dev) == iast` check), a full visual cross-reference of all 59 PDF pages, and an offline Monier-Williams dictionary cross-check (`bootstrap/mw_crosscheck.py`, ~90% confirmed as real MW headwords; flagged source typos corrected — see `bootstrap/qa_visual_report.md` and `bootstrap/mw_crosscheck_report.md`). Residual fixes were made directly in `data/vedanta.json`.

### The vowel sandhi deck

Sandhi splits into three top-level families by what meets at the junction — **vowel** (*svara*, अच्) sandhi (vowel + vowel), **consonant** (*vyañjana*, हल्) sandhi (at least one consonant), and **visarga** sandhi (final ḥ + next sound). This deck is the first; **visarga sandhi** and **consonant sandhi** are each carded as their own decks too (see below), so all three families are now covered.

A deck (`🕉️ Sanskrit Sandhi Joining::1. Vowel`, `Anki::VOWEL_SANDHI_DECK`) of 78 cards teaching five vowel (svara) sandhis — dīrgha, guṇa, vṛddhi, yaṇ, ayādi — front: two parts in Devanagari, space-separated (देव इन्द्र); back: the combined form, IAST of the parts and the whole, which sandhi applied, a one-line rule explanation, and the **context** (see below); no audio. `data/vowel_sandhi.json` is the **committed source of truth** (like `vedanta.json`): `lib/generators/vowel_sandhi.rb` (class `Generators::VowelSandhi`) is a pure reader over it (`VowelSandhiDeck.load`, `lib/vowel_sandhi_deck.rb`), and the engine (`lib/vowel_sandhi.rb`) + `IastDevanagari.valid_pair?` validate every record in `test/vowel_sandhi_deck_test.rb` rather than at generation time. Each record's Devanagari is curated (there is no IAST→Devanagari converter — see the transliterator note above). The examples were chosen from worked examples verified across Whitney, Emeneau & van Nooten, Pāṇini's sūtras, learnsanskrit.org and the Arsha Vidya handouts (a deep-research pass), then re-audited by a second deep-research pass. **Avagraha (word-final e/o + a → ऽ, e.g. te'pi) cards were removed for now** — the engine still implements the rule, so they can be restored by putting `type: "avagraha"` records back into `data/vowel_sandhi.json`.

**35 of the cards come from the Arsha Bodha [Vowel Sandhi Exercise 1](https://arshabodha.org/wp-content/uploads/abc/teachings/SanskritMaterial/Exercises/VowelSandhiExercise-1.pdf) and its [answer sheet](https://arshabodha.org/wp-content/uploads/abc/teachings/SanskritMaterial/Exercises/VowelSandhiExercise-1_answers-1.pdf)** — the same teacher as the consonant handout. Of its 38 items, one (न + एव) the deck already had and one (देव + इन्द्रः) is the existing देव + इन्द्र with a nominative ending, so both were dropped rather than duplicated. A third, तनू + उर्ध्वम्, was **removed after carding**: the sheet prints उर्ध्वम् there (confirmed at 600 dpi and in the सन्धिचन्द्रिका scan the question sheet reproduces) but ऊर्ध्वम् on its own page 1, and ऊर्ध्व is the real word — so the item is a source typo rather than a teaching choice, and a misspelling is not worth carding when the junction it shows (ū + u) is already covered. **Exercise 2 is deliberately NOT carded**: its 36 items are invented syllables (ने + उप → नयुप, भू + ओब → भ्वोब), a systematic yaṇ/ayādi drill rather than Sanskrit, and they could not carry an honest `context` line — भू + ओब is neither a compound, nor two words, nor one word. Each new record's `context` was assigned by a simple rule: a prefix joined to a stem or verb is `internal` (अभि + इष्टम्, प्र + एधते), two nominal stems are `compound` (गण + ईशः), and anything with a free particle, pronoun or finite verb is `external` (न + इति, सा + उवाच).

**The exercise sheets are where the engine earns its keep.** A transcribed item supplies only the two words and the answer; `VowelSandhi.join` then *derives* the combined IAST from the parts, and `IastDevanagari.valid_pair?` checks that the transcribed answer-column Devanagari reads as exactly that. A misread vowel length in any of the three columns fails one of the two checks, so the deck test re-verifies the whole sheet on every run.

`lib/vowel_sandhi.rb` is the pure, tested engine (module `VowelSandhi`). `VowelSandhi.join(word1, word2, type)` splits the junction (final vowel of word 1 + initial vowel of word 2), applies the rule, and returns the combined IAST + rule metadata (`RULES`). The `type` is **validated** against the junction via `candidates(v1, v2)`: a mislabelled pair raises `ArgumentError`, so the curated list is self-checking (a pair tagged `:guna` whose junction is actually i+i fails loudly at build time and in tests). The mappings are `LONG` (dīrgha), `GUNA`, `VRDDHI`, `SEMIVOWEL` (yaṇ), `AYADI`, and avagraha. One transform subtlety: yaṇ and ayādi **keep the second vowel** (the combined form appends the whole `word2`), whereas dīrgha/guṇa/vṛddhi/avagraha consume it.

**Context (the internal/compound/external distinction).** The front shows two pieces, and a vowel junction's outcome can depend on whether the pieces are two free words, the members of a compound (*samāsa*), or a stem+affix inside one word. The four general rules (dīrgha, guṇa, vṛddhi, yaṇ) give the same result in all three, but a **word-final diphthong differs by context**: across a word boundary, e/o + a → avagraha (te'pi) and ai/au reduce or retain — the ay/av of ayādi (ne+ana→nayana) only appears in *derivation* (internal sandhi), never between two free words. So each record carries a `context` field from `CONTEXTS` (`external`/`compound`/`internal`), rendered on the card as "(sandhi between two separate words / within a compound / within a single word)". The two context-bound rules are kept consistent in the data and asserted in the tests: every `:ayadi` pair is `:internal`, every `:avagraha` pair is `:external`. (For the e/o+a junction `candidates` still returns both `:ayadi` and `:avagraha`, so the engine accepts either; the curated label decides and the context tag makes which one explicit.) Most dīrgha/guṇa pairs are compounds — the standard teaching examples — which is honest as long as they aren't presented as sentence-level word pairs. Unattested ḷ junctions (guṇa a+ḷ, yaṇ ḷ→l) are deliberately omitted.

Each record holds the two words and the combined form in both IAST and Devanagari, plus type, context, rule name, explanation and the word meanings (see "Word meanings on the sandhi decks"). Cards are keyed `vowel_sandhi:<type>:<w1_iast>+<w2_iast>`. Add a card by adding a record to `data/vowel_sandhi.json`; `test/vowel_sandhi_deck_test.rb` re-derives it with the engine (which still raises on a mislabelled type↔junction) and checks every Devanagari field with `valid_pair?`.

**The splitting (inverse) deck.** A companion deck (`🕉️ Sanskrit Sandhi Splitting::1. Vowel`, `Anki::VOWEL_SANDHI_SPLIT_DECK`) practises the reverse skill — *vigraha*, splitting a combined form back into its two words. `lib/generators/vowel_sandhi_split.rb` (class `Generators::VowelSandhiSplit`, `--vowel-sandhi-split`) is a pure rendering transform over the **same** `data/vowel_sandhi.json` (no new data file, no engine change): front is the combined Devanagari (देवेन्द्र), back is the split (देव + इन्द्र) plus the same IAST/rule/context info as the forward card, reusing `Generators::VowelSandhi::CONTEXTS`. It is a **separate deck** so the two directions study independently, and its cards are keyed with the distinct `vowel_sandhi_split:` prefix — both decks use `#guid column:1`, so a shared key would make Anki treat the two directions as one note and overwrite on import. This deck is deliberately not carded via Anki's native "Basic (and reversed card)" note type: the forward card's back is a rich teaching panel, which would spoil the prompt on a native reverse. `requires_letters? == false`, no audio, no JSON intermediate. Validated by `test/vowel_sandhi_split_deck_test.rb` (the card data itself is already validated by `test/vowel_sandhi_deck_test.rb`).

### The visarga sandhi deck

A deck (`🕉️ Sanskrit Sandhi Joining::2. Visarga`, `Anki::VISARGA_SANDHI_DECK`) of 86 cards — the second sandhi family. It teaches how a word-final visarga (ḥ) transforms based on the **preceding vowel** (`-aḥ` from `-as`, `-āḥ` from `-ās`, or ḥ on any other vowel) and the **following sound** (voiced consonant, vowel, voiceless stop, sibilant, pause). Front: the two parts in Devanagari, space-separated (नरः गच्छति); back: the combined form(s), IAST of the parts and the whole, which rule applied, and a one-line explanation; no audio. `requires_letters? == false`.

Unlike the vowel-sandhi deck there is **deliberately no derivation engine** (user's call): visarga outcomes are conditioned jointly by the preceding vowel *and* the following sound's category, and were curated by hand from worked examples verified in a deep-research pass (Whitney §§145,152,170,172,174,175,177; Pāṇini 8.3.34, 6.1.132; learnsanskrit.org; ashtangayoga.info — 25/25 claims confirmed, saved in the `[[visarga-sandhi-rules]]` memory).

**word1's underlying (pre-visarga) form is carded.** A final visarga is the pause-form of an original **-s or -r** (Whitney §152), and which one it is decides the sandhi — `naraḥ ← naras` takes the `-aḥ → -o` rule, but `punaḥ ← punar` shows an r (and never `-o`) because it is an r-stem. That distinction is invisible in the visarga spelling, so every record carries `word1_underlying_iast`/`word1_underlying_devanagari` (e.g. `naras`/नरस्, `punar`/पुनर्) and the generator renders it under the front pair (`<small>(नरस्)</small>`). In this deck only `punaḥ` is `-r`; all other word1 forms are `-s`. The deck test validates each underlying Devanagari↔IAST pair and asserts every underlying IAST ends in s or r. `data/visarga_sandhi.json` is the **committed source of truth** and `lib/generators/visarga_sandhi.rb` (class `Generators::VisargaSandhi`, `--visarga-sandhi`) is a pure reader over it (`VisargaSandhiDeck.load`, `lib/visarga_sandhi_deck.rb`) — key `visarga_sandhi:<type>:<w1_iast>+<w2_iast>`. The only validation is `test/visarga_sandhi_deck_test.rb`, which checks structure and runs every stored Devanagari↔IAST pair through `IastDevanagari.valid_pair?`.

**36 of the cards come from the Arsha Bodha [Visarga Sandhi Exercise](https://arshabodha.org/wp-content/uploads/abc/teachings/SanskritMaterial/Exercises/VisargaSandhiExercise.pdf) and its [answer sheet](https://arshabodha.org/wp-content/uploads/abc/teachings/SanskritMaterial/Exercises/VisargaSandhiExerciseAnswers.pdf)**, covering every one of the ten types. Of its 38 items, one (नरः + गच्छति) the deck already had, and one — नरः च बालः च → नरश्च बालश्च — was skipped because it holds **two** junctions and will not fit the two-word schema. **The sheet writes its answers joined (नरस्त्यजति) and they are stored separated (नरस् त्यजति)**, following this deck's own convention of keeping the word boundary visible; where the sheet gives two accepted forms (तैस्सह / तैः सह) both are kept, and where it gives one, one. Unlike the vowel deck there is no engine to re-derive these, so the transcription rests on the image read plus `valid_pair?` on every stored form, including the two-form combinations and each `word1_underlying_*`.

**A per-type explanation is not always safe to copy.** `visarga_retained` explanations are keyed to the *following sound* — jihvāmūlīya before k/kh, upadhmānīya before p/ph, assimilation-is-default before a sibilant — so a new record before प् must take the p-variant, not whichever text the first record of that type happens to carry. `test_retained_cards_explain_the_pronunciation` enforces exactly this and is what caught it.

The ten rule categories (`type`): `as_o_consonant` (-aḥ → -o before a voiced consonant), `as_o_avagraha` (-aḥ + a- → -o with the a elided to ऽ), `as_a_vowel` (-aḥ → -a before other vowels, hiatus kept), `aas_aa` (-āḥ → -ā before any voiced sound, never -o), `visarga_r` (ḥ → r before a voiced sound), `visarga_r_dropped` (ḥ before r-: r elided, preceding short vowel lengthened), `visarga_sibilant` (ḥ → ś/ṣ/s before a voiceless stop), `visarga_retained` (ḥ kept before k/kh, p/ph, a sibilant, or a pause), `sa_esa` (saḥ/eṣaḥ → sa/eṣa before a consonant), and `sa_esa_vowel` (contrast cards: before a *vowel* saḥ/eṣaḥ are not special and take ordinary -aḥ sandhi — so 'ham, sa icchati — sourced from Whitney §176a and learnsanskrit.org).

**Multiple accepted outcomes per junction.** Some junctions have more than one valid combination (before a voiceless stop the visarga may assimilate to a sibilant *or* be retained), so each record's `combined` is a **list** of `{iast, devanagari}` forms — the generator renders every form on the back. This differs from the vowel-sandhi schema (one combined form per record).

**`visarga_retained` is a spelling statement, not a pronunciation one.** All six `visarga_retained` records carry the pronunciation fact in their `explanation` (there is no separate field — the two generators already render `explanation`, so folding it in got both decks for free). Before **k/kh** the retained visarga is optionally the **jihvāmūlīya** (a velar fricative) and before **p/ph** the **upadhmānīya** (a bilabial fricative), per Pāṇini 8.3.37; before a **sibilant** assimilation is in fact the default (8.3.34) with the written visarga the licensed alternative (8.3.36), and the visarga is pronounced at the sibilant's place either way. So all three sub-cases are one phenomenon — the visarga takes the articulation of whatever follows — and only the first two got names. Sources: Whitney §§69, 170, 172 (he is the dissenting voice, calling the two spirants possible "pure grammatical abstractions"), Pāṇini 8.3.34/36/37, learnsanskrit.org, ashtangayoga.info.

**Never use the Vedic Extensions characters.** The jihvāmūlīya and upadhmānīya have their own Unicode signs (ᳵ U+1CF5, ᳶ U+1CF6), and they are **unusable in these decks**: essentially no default font on macOS, iOS, Android or Windows covers the U+1CF0–U+1CFF block, so they render as tofu in Anki and in terminals. Describe the sounds in words instead. `test/visarga_sandhi_deck_test.rb#test_no_vedic_extension_characters` fails the build if any string in `data/visarga_sandhi.json` reintroduces one.

**The splitting (inverse) deck.** A companion deck (`🕉️ Sanskrit Sandhi Splitting::2. Visarga`, `Anki::VISARGA_SANDHI_SPLIT_DECK`) practises the reverse skill — *vigraha*, splitting a combined form back into its two words — mirroring the vowel-sandhi splitting deck. `lib/generators/visarga_sandhi_split.rb` (class `Generators::VisargaSandhiSplit`, `--visarga-sandhi-split`) is a pure rendering transform over the **same** `data/visarga_sandhi.json` (no new data file, no engine): front is the primary combined Devanagari form (नरश् चरति), back is the split (नरः + चरति) plus word1's underlying pre-visarga form (नरः ← नरस्), any alternate accepted forms, and the same rule/explanation as the forward card. Because a record can list several accepted combined forms, the deck emits **one card per record** on the primary form (`combined[0]`) — 86 records → 86 cards — with the alternates shown on the back as "also accepted". It is a **separate deck** keyed with the distinct `visarga_sandhi_split:` prefix (both decks use `#guid column:1`, so a shared key would make Anki merge the two directions on import). `requires_letters? == false`, no audio, no JSON intermediate. Validated by `test/visarga_sandhi_split_deck_test.rb` (the card data itself is already validated by `test/visarga_sandhi_deck_test.rb`).

### The mantra deck

A deck (`🕉️ Sanskrit Mantras`, `Anki::MANTRAS_DECK`) of whole mantras — front: the mantra in Devanagari and nothing else (naming it would give the prompt away); back: every translation (each carrying its own attribution as the label) and a recitation, **and nothing else**. There is deliberately no name/source header, no word-by-word gloss, and no notes on the card — a translation's label is already "the source for the translation," and the deck favours one clean translation + audio over a denser teaching panel. There is also deliberately **no full-line IAST** on the back — `transliteration` stays in the data purely to validate the curated Devanagari, never to be shown. `requires_letters? == false`.

Two cards currently: the **Gāyatrī mantra**, in the full form with `ॐ` and the three vyāhṛtis (`ॐ भूर्भुवः स्वः` + Ṛgveda 3.62.10); and Ādi Śaṅkara's **Prātaḥ Smaraṇa Stotram** (three verses; the traditional closing phala-śruti verse is deliberately not carded, since the deck is about the meditation itself rather than the fruit of reciting it).

`data/mantras.json` is the **committed source of truth** and `lib/generators/mantras.rb` (class `Generators::Mantras`, `--mantras`) is a pure reader over it (`Mantras.load`, `lib/mantras.rb`) — key `mantra:<id>`, no JSON intermediate. Nothing is derived: the Devanagari, its transliteration and the translations are all curated. Each record holds `id`, `name`, `source`, multi-line `devanagari` + `transliteration` (newlines become `<br>` on the card; a blank line — i.e. two consecutive newlines — separates verses), `translations`, `word_meanings`, `notes`, `audio_file` and `audio_source`. **`name`, `source`, `word_meanings` and `notes` are curatorial metadata only** — kept in the data (the latter two for a possible future word deck / footnote use, per the Gita's `word_meanings`) but **not rendered on the card**; `word_meanings` may legitimately be `[]` and `notes` `""` for an entry where per-word glossing isn't worth the effort (e.g. a multi-verse philosophical stotra rather than a short mantra).

**`translations` is an ordered list, not a hash** — `[{label, text}, …]`. The label is what the card prints, so each translation carries its own attribution (`"Griffith (1896)"`) and the generator renders any number of them without knowing their names. The Gayatri card carries **one**, labelled *"after S. Radhakrishnan (1953)"*; the Prātaḥ Smaraṇa card carries **one**, labelled *"Swami Tadatmananda (Arsha Bodha)"* (the translation the audio recitation itself is drawn from).

**Why "after" and not a plain attribution (Gayatri).** The card's feminine "may She inspire our intelligence" is *not* what Radhakrishnan wrote — *The Principal Upanishads* (1953, p. 299) reads "may **he** inspire our intelligence" (verified against two independent Internet Archive scans; the string "may She" occurs nowhere in the book). Wikipedia misquotes it, and the same misquotation circulates for Vivekananda, whose Complete Works in fact read "may **He** enlighten our minds" (checked on Wikisource). The feminine reading was kept deliberately — it is what makes the card land — so `after` marks the wording as adapted rather than putting words in a real author's mouth. **Never promote it to a plain attribution.**

The feminine reading is devotional, not grammatical, and the `notes` field records this (kept for reference; not rendered on the card): the verse's `यः`/`प्रचोदयात्` refer back to the masculine `सवितुः देवस्य`, so *every* translation renders it "he" — **none** of the 71 scholarly translations collected in Dominik Haas, "Translating the Gāyatrī-Mantra" (*Asian Literature & Translation* 10.1, 2023, open access) uses a feminine pronoun. The goddess Gāyatrī is the personified mantra (Veda-mātā), not the referent of `यः` inside the verse. That Haas appendix is the place to look for any future translation choice. General lesson: verify an attributed quote against the source before carding it — the web was wrong about both of these.

**`word_meanings` lists citation forms, not the forms in the text** (`सवितुः`/`savituḥ`, not the `सवितुर्` that appears under sandhi), so each gloss entry is a single word whose spelling is validated strictly. The Prātaḥ Smaraṇa entry has none (`[]`) — a per-word gloss for three verses of running prose isn't worth curating when the card doesn't show it anyway.

**The Prātaḥ Smaraṇa Devanagari has one pada break that falls mid-sandhi**: verse 2's `...निगमा अवोचं / स्तं देवदेवम्...` reads continuously as `nigamā avocaṃs taṃ devadevam` ("the scriptures declared him... the god of gods") — the `स्` that opens the printed fourth line is really the start of `तम्`, carried over because the metre's line break doesn't land on a word boundary. This is recorded in the entry's `notes`, not worked around: the Devanagari is stored exactly as traditionally printed.

`test/mantras_data_test.rb` is the data validator: it checks structure and, crucially, that **the stored Devanagari and the stored IAST are the same text** — the mantra line-for-line via `IastDevanagari.valid_pair?(…, ignore_spacing: true)` (compared per line so a failure points at the wrong line, blank separator lines included — both sides must blank at the same positions), and every gloss word via plain `valid_pair?`. It also asserts the referenced audio is actually committed, and that the Devanagari carries **no Vedic accent marks** (U+0951 udātta, U+0952 anudātta): sources often print a mantra accented, but the marks do not survive the transliteration round-trip and render inconsistently, so the curated text stays unaccented. `test/mantras_test.rb` covers the generator (front is the Devanagari only; back is translations + audio only, nothing else).

### The consonant sandhi decks

The third and last sandhi family (*vyañjana*, हल्), carded as **two** decks split the way the source handout splits it — external (between two words) and internal (within one word):

| deck | constant | flag | rules | cards |
|---|---|---|---|---|
| `🕉️ Sanskrit Sandhi Joining::3. External Consonant` | `Anki::EXTERNAL_CONSONANT_SANDHI_DECK` | `--external-consonant-sandhi` | 12 | 82 |
| `🕉️ Sanskrit Sandhi Joining::4. Internal Consonant` | `Anki::INTERNAL_CONSONANT_SANDHI_DECK` | `--internal-consonant-sandhi` | 2 | 22 |

Each has a **splitting companion** (see below), so the family is four decks in all.

**Every sandhi deck is a subdeck** of `Anki::SANDHI_JOINING_PARENT` (`🕉️ Sanskrit Sandhi Joining`) or `Anki::SANDHI_SPLITTING_PARENT` (`🕉️ Sanskrit Sandhi Splitting`), each holding the same four numbered families (see "Deck layout"). The forward consonant generator tests assert their deck sits under the joining parent. (Splitting decks used to be marked by a `(Splitting)` suffix instead, which is why older text calls them "the splitting deck" as if that were a name.)

**The source of truth is the Arsha Bodha Center ["Consonant Sandhi" handout](https://arshabodha.org/wp-content/uploads/abc/teachings/SanskritMaterial/Sandhi/ConsonantSandhiRules.pdf)** (Swami Tadatmananda — the same teacher as the Prātaḥ Smaraṇa recitation in the mantra deck), which the user is studying from: 12 external rules and 2 internal ones, each with one worked example. The handout drives what is carded and how the forms are spelled; a research pass over four independent sources (Whitney's Grammar Ch. III §§139–210, Ruppel's *Cambridge Introduction to Sanskrit* sandhi grid, Guy Leavitt's *Saṁskṛtasubodhinī* Lesson 13 handout after Coulson, and learnsanskrit.org's external/internal references) corroborated all 12 external rules with no additions or contradictions, and supplied the three further examples per rule. Every record's `source` field names where that example came from. **The handout's own PDF is a legacy glyph font** — `pdftotext` yields mojibake, so it was read by rendering the page to an image (`pdftoppm -r 200 -png`), the same problem the Vedanta glossary PDF had.

**The same teacher's [exercise sheet](https://arshabodha.org/wp-content/uploads/abc/teachings/sanskrit/ConsonantSandhiExercise-1.pdf) and [answer sheet](https://arshabodha.org/wp-content/uploads/abc/teachings/sanskrit/ConsonantSandhiExercise-answers-1.pdf) supply 30 further external examples** (`"source": "exercise sheet"`), taking that deck from 53 to 82 cards. The sheet is **external only** — its subtitle reads "use rules for external sandhi only" — so it contributes nothing to the internal deck; the anusvāra in its items (गुरूंश्छन्दान्, एतांश्च, गच्छंल्लोकम्) is the म्/न् of rules 6/8/9, not the intervening anusvāra of ṣatva. Its 31 items touch all 12 rules, unevenly — six for rule 1 down to one each for rules 5, 9 and 12. Exactly one item (वनम् गच्छति) the deck already had, and it was dropped rather than duplicated; no merged record shares a word pair, a combined form or a key with another. **Both PDFs have the same legacy-glyph problem**: the exercise sheet yields pure mojibake (`z$( EeëyR`) and the answer sheet decodes only partially and lossily (जगद्दाता comes out as `जग"ाता`), so both were read by rendering to PNG, and every item was transcribed twice — at 200 dpi and again from 400 dpi crops — before being carded. The answer sheet prints the input pair beside its answer, so re-reading it checks both columns at once. Every transcribed pair was then run through `IastDevanagari.valid_pair?`, which is what the deck test re-checks on every run.

**One exercise item was dropped as a source typo**: सन् + टिपण्णी → संष्टिपण्णी, where the ordinary word is टिप्पणी (*ṭippaṇī*). The sheet spells it टिपण्णी in both its columns, but the *visarga* exercise from the same teacher spells the same word टिप्पणी correctly (शास्त्रः टिप्पणी → शास्त्रष्टिप्पणी, now in the visarga deck), which settles it. Carding a misspelling is not worth one sub-case, so **न् + ट् → ंष्ट् is now uncarded** — rule 8 still has 7 cards covering च् and त्, and its rule text states the ट् case.

`data/external_consonant_sandhi.json` and `data/internal_consonant_sandhi.json` are the **committed sources of truth**; `lib/generators/{external,internal}_consonant_sandhi.rb` are pure readers over them (via `ExternalConsonantSandhiDeck.load` / `InternalConsonantSandhiDeck.load` in `lib/`). Keys are `external_consonant_sandhi:<type>:<w1_iast>+<w2_iast>` and `internal_consonant_sandhi:…`. Both `requires_letters? == false`, no audio, no JSON intermediate.

**No derivation engine** — the same call as the visarga deck. The outcomes are curated; `test/{external,internal}_consonant_sandhi_deck_test.rb` are the only validation, checking structure and running every stored Devanagari↔IAST pair through `IastDevanagari.valid_pair?`. All 76 records validate under the **strict** validator — no `ignore_spacing:` leniency and, notably, **no change to `lib/iast_devanagari.rb` was needed at all**.

**Why no anunāsika support was needed.** Whitney (§206) writes the न् + ल् junction with the anunāsika (त्रीँल् लोकान्), which `to_iast` cannot read (U+0901 is unmapped). The handout instead writes that junction as **anusvāra + ल्** — एतान् लोकान् → एतांल्लोकान् — which the reader already handles, since an anusvāra before a semivowel correctly stays `ṃ`. Following the handout's spelling avoided touching the transliterator. If anunāsika cards are ever wanted, `to_iast` needs a U+0901 mapping first.

**The 12 external rules → 13 `type` values.** The handout's rule 3 covers palatals and cerebrals on one line, and those are two different junctions, so they are carded separately: `hc_voicing` (1), `hc_nasal` (2), `t_palatal` + `t_cerebral` (3), `t_l` (4), `t_sha` (5), `m_anusvara` (6), `n_nasal` (7), `n_anusvara_sibilant` (8), `n_l` (9), `nasal_doubling` (10), `stop_ha` (11), `cha_doubling` (12). Each record carries the handout's `rule_number`, and the deck test asserts type↔rule_number agreement and that **every** rule still has cards, so a rule cannot silently lose its coverage. The internal deck's two types are `satva` (स् → ष्) and `natva` (न् → ण्).

**The ṇatva rule is carded with its full three-part condition,** which the handout's one-line statement (`ष् र् ऋ + न् → ण् (many conditions)`) leaves implicit. All three parts were verified against Pāṇini 8.4.1 (`रषाभ्यां नो णः समानपदे`) + 8.4.2 (`अट्कुप्वाङ्नुम्व्यवायेऽपि`), Whitney §189, learnsanskrit.org's internal-sandhi chart, Open Pathshala and Sanskrit Studio — all agree:

1. **Trigger:** र् ऋ ॠ or ष् earlier in the same word (`समानपदे` — this is why it is *internal* sandhi). Note it is **ष्**, the retroflex sibilant, never श्.
2. **What follows the न्:** a vowel, or न् म् य् व् (the sonorants). This is why a word-final न् never retroflexes.
3. **What may intervene:** vowels, क-varga, प-varga, य् व् ह्, anusvāra. Anything else — palatal, cerebral, dental, ल् श् स् — blocks it. (Pāṇini's `अट्` also admits र् itself and the prefix आ/`आङ्`; both are subsumed by the teaching statement above.)

**ṣatva is stated with its three conditions too, and the contrast between the two rules is the point.** Verified against Whitney §§180–181, Pāṇini 8.3.57–8.3.59 (`इण्कोः`, `नुम्विसर्जनीयशर्व्यवायेऽपि`, `आदेशप्रत्यययोः`), learnsanskrit.org and Sanskrit Studio: (1) the sound **immediately** before the स् is a vowel other than अ/आ, or क-varga, र् or ल्; (2) the स् is neither word-final (`अपदान्त`) nor followed by र् (whence Whitney's *usra, tisras, tamisra*); (3) only anusvāra, visarga or a sibilant (`नुम्`, `विसर्जनीय`, `शर्`) may intervene. **That third condition is where the two rules diverge sharply** — ṇatva reaches across vowels, क-varga, प-varga, य् व् ह् and anusvāra, whereas ṣatva's trigger must otherwise be immediately adjacent. The cards say so explicitly, because the two rules otherwise look parallel. `हिंस्`/`पुंस्` are noted as lexical exceptions.

The 11 ṣatva cards cover every trigger and the one cardable intervener: विषीदति/अभिषिञ्चति (इ), धनुषा/सुषुप्तः (उ), **वाक्षु** (क्), **चतुर्षु** (र्), **पितृषु** (ऋ), **जुहोषि** (ओ, Whitney §184), **हविःषु** (visarga intervening), plus **अग्निषु / वाक्षु / मरुत्सु** — a deliberate trio on the one ending -सु where the trigger is a vowel, then क्, then त् (which is not a trigger, so मरुत्सु keeps its dental स् and is flagged `contrast`). **Two ṣatva cases are deliberately uncarded, and the rule text states them instead.** Condition 2's "not followed by र्": no suffix begins with स्र, so its only examples are lexical (*usra, tisras, tamisra*) and there is no honest two-part card for it. And condition 3's **anusvāra intervening**: every example is the neuter nom./acc. plural of an s-stem (हवींषि, चक्षूंषि, ज्योतींषि), where the anusvāra is the **नुम् augment** those cases insert and the stem vowel lengthens with it (Whitney §§379b, 413, verified against the Wikisource page scans) — two steps from outside this rule that a card must explain before its ṣatva is even visible, which is why the हवींषि card was dropped. Both gaps are recorded in `REQUIRED_COVERAGE`, so neither can be mistaken for an oversight. This mirrors the ṇatva gap below.

**Every record therefore carries two extra fields.** `analysis` is a one-line breakdown rendered under the explanation in `<small>` (`trigger ऋ · through ग् आ (क-varga + vowel) · न् before आ`), and `covers` is a list of tags naming which of the conditions that example demonstrates. `test_natva_examples_cover_every_condition` asserts the union of `covers` spans `REQUIRED_COVERAGE` — every trigger, every permitted intervening class, and both failure modes — so **swapping out an example cannot silently drop a case from the deck**. `REQUIRED_COVERAGE` is keyed by type, so both rules are guarded independently, and the tags are range-checked — a typo'd tag fails as a missing case rather than quietly counting for nothing. `FAILURE_TAGS` additionally ties each way a rule can fail to a card flagged `contrast`.

The 11 ṇatva cards are likewise chosen for coverage: ब्रह्मणा (ह् + प-varga), रामेण (प-varga), विषेण (**ष्** trigger), गुरुणा (bare vowel), मृगाणाम् (**ऋ** trigger + **क-varga**), कार्याणि (**य्**), सर्वाणि (**व्**), बृंहण (**ऋ** trigger + **anusvāra** + ह्), चरण, plus two contrast cards. **चर् + अन → चरण and चर् + अन्ति → चरन्ति are a deliberate minimal pair** — same trigger, same intervening vowel, differing only in what follows the न् — which is the cleanest way to teach condition 2; the second is flagged `contrast`. The other contrast card, अर्जुन + एन → अर्जुनेन, fails condition 3 on the intervening palatal ज्.

**Combined forms are written JOINED** (तत् + च → तच्च), the way the handout writes them and the way sandhi actually appears in a printed text — unlike the vowel/visarga decks, which keep the word boundary visible (नरश् चरति). The IAST line (`tat + ca → tacca`) carries the analysis instead. As in the visarga deck, `combined` is a **list** of `{iast, devanagari}` because a junction can have several accepted outcomes (तत् + हि → तद्धि *or* तद् हि; ch-doubling is optional after a long vowel: नदीच्छाया / नदी छाया).

**word1's citation form is carded, but only where the padānta reduction changed it.** A word may end only in `k ṭ t p ṅ n m ḥ`, so वाच् can only *end* a word as वाक् and षष् as षट् — a reduction that must happen before any junction rule applies, and which is invisible in the sandhi-final spelling. The nullable `word1_underlying_iast`/`word1_underlying_devanagari` hold it, rendered under the front as `<small>(वाक् ← वाच्)</small>`, mirroring the visarga deck's `(नरस्)`. It is **null** where nothing changed (तत्, फलम्, एतान्), and the deck test asserts the pair is either both-set or both-null and never identical to word1. This is why **padānta reduction has no deck of its own**: the handout has no such section, and this field teaches it in context. A dedicated word-final-forms deck remains a plausible future addition (it could not have a splitting companion — वाक् ← वाच्/वाक्/वाग् is ambiguous).

**Contrast cards carry their own rule text.** Four records show a junction where the rule deliberately does *not* fire: एतान् + इह → एतानिह (no doubling, because the vowel before the nasal is long), चर् + अन्ति → चरन्ति (ṇatva blocked because the न् is followed by त्) अर्जुन + एन → अर्जुनेन (ṇatva blocked by the intervening palatal ज्) and मरुत् + सु → मरुत्सु (ṣatva blocked because त् is not a trigger). They are flagged `"contrast": true`, and both deck tests assert a contrast card does not reuse its type's default `rule`/`explanation` — the default text would state a rule its own answer contradicts. The flag is also what exempts the अर्जुनेन card from the internal test's assertion that a ṇatva result actually contains ण.

**The splitting (inverse) decks.** Both families have a companion deck practising *vigraha* — splitting a combined form back into its parts — following the vowel and visarga splitting decks exactly: a pure rendering transform over the **same** data file (no new data, no engine), a subdeck under `🕉️ Sanskrit Sandhi Splitting`, and a distinct `*_split:` key prefix so Anki's `#guid column:1` does not merge the two directions.

| deck | constant | flag | cards |
|---|---|---|---|
| `🕉️ Sanskrit Sandhi Splitting::3. External Consonant` | `Anki::EXTERNAL_CONSONANT_SANDHI_SPLIT_DECK` | `--external-consonant-sandhi-split` | 81 |
| `🕉️ Sanskrit Sandhi Splitting::4. Internal Consonant` | `Anki::INTERNAL_CONSONANT_SANDHI_SPLIT_DECK` | `--internal-consonant-sandhi-split` | 19 |

`lib/generators/{external,internal}_consonant_sandhi_split.rb` (classes `Generators::ExternalConsonantSandhiSplit` / `Generators::InternalConsonantSandhiSplit`). The external front is the primary combined form written joined (वाग्देवी) and the back is the two words (वाक् + देवी), the IAST, word1's citation form where the padānta reduction changed it (वाक् ← वाच्), any alternate accepted forms, and the same rule/explanation as the forward card. The internal front is the finished word (विषीदति) and the back is its morphemes (वि + सीदति) plus rule, explanation and the `analysis` line — which names the trigger, and so is precisely what tells the reader the ष् in front of them is an underlying स्. As in the visarga splitting deck, a record with several accepted outcomes yields **one** card, prompting on `combined[0]` with the alternates named on the back. `requires_letters? == false`, no audio, no JSON intermediate.

**Contrast records are deliberately not carded in this direction** (the user's call): splitting मरुत्सु or एतानिह at its obvious seam teaches nothing the forward card didn't, since the whole point of those records is a rule that never fired. So `build` is the loader minus `contrast` records — 82 → 81 and 22 → 19 — and each split deck test asserts both that no contrast record was carded and that the fixture still contains some, so the filter cannot quietly become a no-op. Validated by `test/{external,internal}_consonant_sandhi_split_deck_test.rb` (the card data itself is already validated by the forward decks' tests).

### Word meanings on the sandhi decks

Every record in the four sandhi data files (`vowel_sandhi`, `visarga_sandhi`, `external_consonant_sandhi`, `internal_consonant_sandhi`) carries three curated strings — `word1_meaning`, `word2_meaning`, `combined_meaning` — and all eight sandhi generators (forward + splitting) render them on the back, just under the IAST line, via the shared `SandhiMeanings.html` (`lib/sandhi_meanings.rb`): `deva “god” + ālaya “abode” → devālaya “temple”` (every deck, splitting included, shows the parts first, then the whole, so the gloss reads the same way everywhere). What `combined_meaning` is depends on the deck: a **definition** for a compound (vowel deck, some external), a **phrase translation** for two free words (`naro gacchati` “the man goes”; visarga and external), and for the internal deck and the vowel deck's ayādi records the affix half is a **grammatical label** (`su` “locative plural ending ('in, among')”, `ana` “action-noun suffix”) because an ending has no dictionary meaning of its own. The quotes are curly on purpose: an ASCII `"` opening a TSV field would be read as a quoted field. `test/sandhi_meanings_test.rb` requires all three fields on every record (no ASCII quotes, tabs or markup) and checks every generator shows them on the back and never on the front, so **a new sandhi record must come with its meanings.**

A few exercise-sheet items are glossed as printed rather than "corrected": उभा + ईशः → उभेशः (the sheet's reading, verified at 150 dpi; उमेशः "lord of Umā" is the likely intent, and the gloss says so) and अनु + उपम → अनूपम (not to be confused with अनुपम "incomparable", from अन्- + उपम). Glosses were drafted from general Sanskrit knowledge, not a per-word dictionary pass; correct any in the data file directly.

### The numbers deck

A deck (`🕉️ Sanskrit Numbers`, `Anki::NUMBERS_DECK`, `--numbers`) of 126 cards on the number system. `data/numbers.json` is the **committed source of truth** and `lib/generators/numbers.rb` (class `Generators::Numbers` — note the top-level loader module is also `Numbers`, `lib/numbers.rb`, so the generator refers to it as `::Numbers`) is a pure reader over it. No audio, no JSON intermediate, `requires_letters? == false`. Keys are `numbers:<kind>:<id>`.

**Design principle: core + rules + exceptions, not the full grid.** A research pass (Whitney §§475–489, learnsanskrit.org, Monier-Williams, the Arsha Bodha ["Numerals" handout](https://arshabodha.org/wp-content/uploads/abc/teachings/SanskritMaterial/Basics/5-6-25-Numerals.pdf), Ruppel's and Samskrita Bharati's sequencing) found the system is ~20 building blocks plus "unit + ten, by ordinary sandhi", with a small set of irregular stems (ekā- in 11 only; dvā- 12/22/32; trayas- 13/23/33; aṣṭā- 18/28/38; ṣoḍaśa; dvi-/tri- only in 82/83; ṣaṇṇavati). So the deck cards the building blocks (1–10, the tens, 100, 1000), **all of 11–19** (18 is the Gita's number), the irregular/sandhi-affected compounds plus a few regular contrasts (21, 25), the ūna-/ekona- "less one" forms for the nines, and 108 (aṣṭottaraśatam) — and deliberately **not** the regular 21–99 grid, which is predictable once the rule is known. The sections of the data file:

- `digits` — ०–९ → value + word. `numerals` — multi-digit numbers and Gita verse references (२.४७, ॥१८.६६॥) → their reading.
- `cardinals` — **two cards each** (word → number, number → word) with distinct `numbers:word:`/`numbers:number:` keys. Optional `parts`, `stem` (ṣaṣ for ṣaṭ), `alternates`, `explanation`, and `gender_forms` (m/f/n nominatives, **only for 1–4**, the only numbers that inflect for gender — per the Arsha Bodha handout tables).
- `ordinals` — 1st–18th carded in their **Gita colophon form** (प्रथमोऽध्यायः → "chapter 1"), the number form a Gita reader meets most; the test asserts each colophon is built from its own ordinal stem (-a → -o 'dhyāyaḥ).
- `rules` — three question → rule cards (how 11–99 are built, ūna-/ekona-, uttara/adhika above 100).

**Deferred, not forgotten:** full declension tables of 1–4, feminine ordinals (prathamā, caturthī…), number adverbs (sakṛt, dviḥ, triḥ, -kṛtvas, -dhā, -śas), ayuta/lakṣa/koṭi.

**Do not copy number lists from the web without validation.** sanskritdocuments.org's 1–100 list has at least six sandhi errors (षड्नवति for षण्णवति, त्र्यस्त्रिंशत् for त्रयस्त्रिंशत्, …); `test/numbers_data_test.rb` runs every stored form through `IastDevanagari.valid_pair?` and catches exactly that class of mistake. It also checks that digits agree with their values, that the core/teens sections are complete, and that rule examples agree with the carded forms. `test/numbers_test.rb` covers rendering (neither direction's front spoils its answer).

### The case-function (vibhakti) decks

The start of declension, built from the Arsha Bodha Beginning Sanskrit Grammar class (taught by Vasanthiji; handouts listed at <https://arshabodha.org/teachings/sanskrit-grammar/>, recordings in the YouTube playlist "Grammar Class N"). The class teaches what each case is *for* (handout [`Vibhakti_1.pdf`](https://arshabodha.org/wp-content/uploads/abc/teachings/SanskritMaterial/Declensions/Vibhakti_1.pdf), "Sanskrit Case Functions") before the endings, so these decks card the functions only, with **no endings** — those are the declension decks (see below).

Three decks, **one per skill, nested under one parent** with Anki's `::` (`Anki::CASE_FUNCTIONS_PARENT` = `🕉️ Sanskrit Case Functions`) — the user's call to split them — numbered in study order (names → uses → examples), the same subdeck convention as the sandhi decks:

| deck | constant | flag | key prefix | cards |
|---|---|---|---|---|
| `…::1. Names` | `Anki::CASE_NAMES_DECK` | `--case-names` | `case_name:{sanskrit,english}:` | 16 (8 cases × both directions) |
| `…::2. Uses` | `Anki::CASE_USES_DECK` | `--case-uses` | `case_use:` | 40 (one per handout use) |
| `…::3. Examples` | `Anki::CASE_EXAMPLES_DECK` | `--case-examples` | `case_example:` | 71 |

`data/case_functions.json` is the **committed source of truth** (sections `cases`, `uses`, `examples`) and the three generators (`lib/generators/case_{names,uses,examples}.rb`) are pure readers over it via `CaseFunctions.load` (`lib/case_functions.rb`, which also holds the shared rendering helpers `case_label`, `bold_target`, `english_html`). No audio, no JSON intermediate, `requires_letters? == false`.

- **`uses` is exactly the handout's numbered list** (1a–1e, 2a–2d, 3a–3j, 4a–4f, 5a–5e, 6a–6e, 7a–7d, 8a), asserted by the data test, so a card's "2c" is the learner's handout's 2c. Each use has a `description` (the handout's wording, shown on the back) and a `question` (the front), and the data test asserts no question names its own case — 7d originally quoted सति सप्तमी and gave the answer away. Uses with no example on the handout (3f, 3h, 4f, 5e, 6c, 6d, 7d) still get a card, just with no example on the back.
- **Example cards put the English on the front** (target word underlined, as the handout does) next to the Devanagari (target in bold). This is deliberate: the learner can't yet read the endings, and the deck tests the *function*. Each example names its target's stem, gender and number on the back; `source` records where it came from (`handout`, `class 13`, or `Goldman reading, Lesson N`).
- **The Rāmāyaṇa examples come from Goldman's *Devavāṇīpraveśikā* reading sections**, which is what the class reads (scans at `…/SanskritMaterial/Reading/Ramayana{1..18}-Lesson-{4..21}.pdf`; the course culminates in reading the Rāmāyaṇa). Lessons 4–7 are carded so far, including several lines of the Lesson 5 memorisation verse रामो राजमणिः सदा विजयते… (memorised in class 26). One sentence is simplified from a relative clause and its `source` says "(adapted)".
- **Sandhi is broken** in every sentence, as on the handout (रामः वनं गच्छति), so every sentence validates under the **strict** `valid_pair?` and the target is a whole space-separated word (`bold_target` matches whole tokens; the data test asserts the target occurs exactly once in both scripts).
- **The vocative is named, not numbered**: per Pāṇini it is the nominative used for address, so the Names card says "listed 8th, after the seven numbered cases" and carries the note. Its IAST is `sambodhanam`, not `saṃbodhanam`: `to_iast` reads the anusvāra before ब as the homorganic m.
- Text uses curly quotes; the data test forbids ASCII `"` (a TSV field opening with one is read as quoted), tabs and markup.

Validated by `test/case_functions_data_test.rb` (structure, handout numbering, every Devanagari↔IAST pair) and `test/case_functions_test.rb` (rendering; no front spoils its answer; keys unique across all three decks, since all use `#guid column:1`).

### The declension decks

The endings, from the Arsha Bodha [`BasicTerminations.pdf`](https://arshabodha.org/wp-content/uploads/abc/teachings/SanskritMaterial/Declensions/BasicTerminations.pdf) handout and class 15 (transcript via `yt-dlp --write-auto-subs`). Three decks under `Anki::DECLENSIONS_PARENT` (`🕉️ Sanskrit Declensions`); each later model-noun handout (रामः/फलम्, शाला/दासी, …) is meant to be the next numbered subdeck.

| deck | constant | flag | key prefix | cards |
|---|---|---|---|---|
| `…::1. Endings` | `Anki::BASIC_ENDINGS_DECK` | `--basic-endings` | `basic_ending:` | 25 (21 m/f cells + vocative + 3 neuter) |
| `…::2. Shared Endings` | `Anki::SHARED_ENDINGS_DECK` | `--shared-endings` | `shared_ending:` | 14 (one per distinct ending) |
| `…::3. त्-Ending Nouns` | `Anki::T_NOUNS_DECK` | `--t-nouns` | `t_noun:` | 120 (5 nouns × 24 cells) |

`data/declensions.json` is the **committed source of truth** (`endings` = the m/f table, 8 cases × 3 numbers incl. the vocative row; `neuter_endings` = the neuter's own nom/acc/voc − ई इ; `sandhi` = the text per change; `nouns` = each noun with all 24 forms and a `sandhi` tag per form). `lib/declensions.rb` (`Declensions`) loads it and holds the shared helpers (`ending` picks the neuter override by gender, `shared_endings` groups cells by ending, `ending_html` puts a bare ः on the dotted circle and spells out the empty neuter ending). Case names come from `data/case_functions.json` so they match the case-function decks. No audio, no JSON intermediate, `requires_letters? == false`.

- **No Pāṇini sup names** (सु औ जस्…): neither the handout nor the class uses them (the user's call). The nominative singular is shown as the handout prints it, ः, with a note that the underlying ending is स्.
- **The nouns are the class's**: मरुत् (m) and जगत् (n) were declined in class; इन्द्रजित् (m), विद्युत् (f) and बृहत् were the homework — बृहत् is an adjective that the teacher asked to be declined **as a neuter**, which is why it has no strong stem (बृहन्तम्) here. Every cell is carded, vocative included (the user wanted the extra practice).
- **The teacher calls the त् → द् before भ् "internal sandhi"**; technically the stem is treated as a pada before भ्/सु endings. The card text describes the change ("a hard consonant followed by a soft one becomes soft") and points at external consonant sandhi rule 1 without picking a label.
- **Every form is re-derived** by `test/declensions_data_test.rb` from stem + the handout ending for that cell and gender + its sandhi tag (`s_dropped`, `no_ending`, `voicing`, `hard_su`, `num`), and the tag itself is re-derived too, so a typo'd form or tag fails; the test also pins the endings table to the handout and runs every Devanagari through strict `valid_pair?`. This only works because all the nouns are त्-stems — a vowel-stem handout (राम) will need its own derivation or a plainly curated table. `test/declensions_test.rb` covers rendering (no front spoils its answer, keys unique across the three decks).

### Mantra audio is committed and trimmed by hand

Unlike the Gita recitations, mantra audio **is committed** (`data/mantra_audio/`, one short clip per mantra, not gitignored) — so `Generators::Mantras` needs no `ensure_audio!` download hook, and the deck works straight from a clone. The Gita's GitHub-release tarball only exists because 640 clips / ~289 MB cannot be committed; two clips (~600 KB and ~4.5 MB) can.

It is also **not fetchable at generation time**, because each clip is an edit of its source rather than the source itself. `data/mantras.json` therefore records `audio_source` (`url`, `credit`, `trim`) for every clip, and a `bootstrap/trim_*_audio.sh` script per clip is the runnable derivation — it re-downloads the source and regenerates the committed mp3. Like the rest of `bootstrap/`, these are not part of the runtime.

The **Gayatri** clip (`bootstrap/trim_mantra_audio.sh`, with `bootstrap/trim_mantra_audio.py`) is Shri Rattan Mohan Sharma's sung rendition (via the Internet Archive), whose 1:19 source is three passes of the mantra over a continuous drone — its envelope autocorrelates at 24.3 s, with vocal attacks at 3.44 / 27.74 / 52.0 s — cut to the single invocation `3.10 → 27.73 s`. The drone is still sounding at the cut, so the clip is faded out (0.5 s) rather than hard-cut, and faded in (0.15 s) because it starts mid-drone. **Its trim toolchain deliberately avoids ffmpeg**, which is not reliably installed (it was in fact broken on the machine this was cut on). It uses only what macOS ships — `afconvert` to decode, `python3` (stdlib `wave`) to cut and fade — plus `lame` for the mp3 encode at 192 kbps CBR, matching the source bitrate.

The **Prātaḥ Smaraṇa** clip (`bootstrap/trim_pratah_smarana_audio.sh`, reusing the same `trim_mantra_audio.py`) is Swami Tadatmananda's recitation (Arsha Bodha Center, chanted in Rāga Bhairav) from [his own YouTube channel](https://www.youtube.com/watch?v=cqPlGaHQUNQ). A YouTube video isn't a direct file, so this one needs `yt-dlp` to fetch it — which shells out to ffmpeg to extract/decode the audio, unlike the Gayatri clip's curl-only fetch. (ffmpeg had to be repaired here too — `brew install x265` fixed a missing shared library — so it isn't reliably available either; `yt-dlp` is a genuinely new dependency, not part of the "ffmpeg-free" toolchain.) The ~233.65 s source is essentially one continuous take of all three verses — silence-detection found no clean inter-verse gaps (only a single sub-half-second breath pause around 88 s) and it already fades in/out naturally at both ends — so the trim keeps nearly the whole file (`0.0 → 233.60 s`) with just a short fade (0.05 s in / 0.5 s out) added on top of the natural roll-off, re-encoded at 160 kbps CBR to match the source's ~153 kbps Opus.

### Audio filename quirk

Local audio filenames mirror the **server's** filenames, not the internal IDs (e.g. `Da` → `d2a.mp3`, `ka` → `k1a.mp3`). This is intentional: macOS's case-insensitive default filesystem would otherwise collapse `Da.mp3` and `da.mp3` into one file. The Anki `[sound:...]` tag in generated cards therefore references the server filename via `letter["audio_file"]`.

### TSV formatting constraint

Generators build card HTML without inline `style="..."` attributes — semicolons inside styles collide with parsers reading the TSV as semicolon-separated. Use `<big>`, `<center>`, `<b>`, `<ul>` instead. `Anki.write_deck` additionally flattens any stray tab inside a field to a space so it cannot break the column split. `clean_tips_html` (private to `lib/generators/basic.rb`) rewrites the source page's `coloredletter1`/`coloredletter2`/`tipsmallfont` spans to `<b>`/`<i>`/`<small>` and strips remaining spans.

### Anki media folder discovery

`lib/media.rb`'s `find_media_dirs` probes the standard Anki base folders per platform — macOS `~/Library/Application Support/Anki2`, Windows `%APPDATA%\Anki2`, Linux `$XDG_DATA_HOME`/`~/.local/share/Anki2`, and Flatpak `~/.var/app/net.ankiweb.Anki/data/Anki2` — and globs each for `*/collection.media`, so any profile is found. `choose_media_dir` prefers Anki's default `User 1` profile when several exist. The `ANKI_MEDIA_DIR` env var overrides everything with an explicit `collection.media` path. Locations are per the [Anki manual](https://docs.ankiweb.net/files.html); update `find_media_dirs` if Anki changes them.
